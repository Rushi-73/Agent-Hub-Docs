Regression Prevention & Detection Plan

Web Application  |  Frontend: React 19  |  Backend: .NET 8 API  |  GitLab CI/CD

1. Problem Statement

Issue: After new releases, some functionality from previous releases breaks unexpectedly. Recent examples caught by QA: a UI popup stopped working correctly, and a wrong condition in the backend affected existing behavior. The root cause of each regression is hard to trace back to a specific change.

2. Why This Is Happening

Process

Commits and merge requests are not linked to work item tickets, so it's hard to trace which change caused an issue.

Process

Regression testing is fully manual — not scalable and prone to missed cases as the product grows.

Testing

No regression test suite exists. Unit test coverage is partial, so changes to shared code go unverified.

Environment

No environment that mirrors production, so issues are often found late, close to or after release.

Part A — Immediate / Already Built Code

Catch existing regressions without rewriting tests from scratch

Prevent regressions in all future releases

4. Rollout Timeline

Immediate (This Sprint)

Change-impact report between last two release tags + API contract diff (oasdiff). No test writing needed — shows exactly where the risk is.

Week 1–2

Set up old-vs-new API response comparison for backend; start screenshot comparison for key UI screens and popups.

Week 2–4

Introduce MR template with ticket linking + impact section; enable "pipeline must pass" before merge.

Month 1–2

Build Playwright regression suite for top 10–20 critical flows (using QA's recorded sessions as a starting point).

Month 2–3

Add diff-coverage gate in CI, staging environment matching production, and feature flags for risky changes.

Ongoing

Rule: every bug found by QA gets an automated test added before closing, so it can't silently reappear.
