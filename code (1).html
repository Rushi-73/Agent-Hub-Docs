Regression Prevention Plan – Future Releases

Web Application  |  Frontend: React 19  |  Backend: .NET 8 API  |  GitLab (Repo, Work Items, CI/CD)  |  Free / Open-Source Tools Only

1. Problem Statement

Issue: When a new release goes out, some existing functionality from earlier releases breaks. QA usually finds these regressions late. Recent examples: a UI popup behaved incorrectly and a backend condition was wrong. Both were caused by new code changes, and it is hard to trace which change caused which issue.
Goal: Prevent regressions before release, and make it quick to trace any regression to the exact change and ticket that caused it.

4. Solution Details

1Link Every Change to a Ticket

  • Branch naming: feature/123-popup-validation, where 123 is the work item ID
  • MR template: every MR must state the ticket, what changed, which existing features could be affected, and the regression risk
  • CI check: the pipeline fails if the MR doesn't reference a ticket
Why: The "Areas that could be affected" field makes developers think about impact on old features before merging.
View MR template (.gitlab/merge_request_templates/Default.md) 
## Related ticket
Closes #<ticket-id>

## What changed
-

## Areas that could be affected (existing features)
-

## Regression risk: Low / Medium / High

## Checklist
- [ ] Unit tests added/updated
- [ ] Existing features touched by this change were tested
- [ ] API contract changes communicated to frontend
View CI ticket-link check (.gitlab-ci.yml) 
check-ticket-link:
  stage: .pre
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - echo "$CI_MERGE_REQUEST_DESCRIPTION" | grep -Eq "#[0-9]+" || (echo "MR must reference a ticket" && exit 1)

2Tag Releases & Add a Staging Environment

  • Tag every release from the release branch (v1.4.0, v1.5.0, ...)
  • List everything that went into a release with one command, which gives a ticket list per release
  • Staging / QA environment: deploy each release candidate there before production, using config and data close to production
  • When something breaks, git bisect between two tags finds the exact commit quickly
View commands 
# What changed between two releases
git log v1.4.0..v1.5.0 --oneline --merges

# Find the exact commit that introduced a bug
git bisect start v1.5.0 v1.4.0

3Build an Automated Regression Suite (Start Small)

  • Key rule: every bug QA finds gets an automated test before the ticket is closed, so the same regression can't come back
  • Start with the most critical flows, not full coverage
LayerToolStart With
Backend unitxUnit (+ Moq / NSubstitute)Business rules and conditions
Backend API integrationWebApplicationFactory + TestcontainersMain endpoints
Frontend componentVitest + React Testing LibraryPopups, forms, validations
End-to-endPlaywright10–20 critical user flows
Highest value: Playwright end-to-end tests replace a large part of QA's current manual regression testing.
Example: backend condition bug test (xUnit) 
[Theory]
[InlineData(0, false)]
[InlineData(1, true)]
[InlineData(100, true)]
[InlineData(-1, false)]
public void IsEligible_ReturnsExpectedResult(int value, bool expected)
{
    var service = new EligibilityService();
    Assert.Equal(expected, service.IsEligible(value));
}
Example: UI popup bug test (Vitest + React Testing Library) 
test('shows confirmation popup when delete is clicked', async () => {
  render(<UserList />);
  await userEvent.click(screen.getByRole('button', { name: /delete/i }));
  expect(screen.getByRole('dialog')).toBeVisible();
  expect(screen.getByText(/are you sure/i)).toBeInTheDocument();
});

4Require Coverage on New Code Only

  • Raising coverage for the whole codebase is slow. Instead, require tests for the lines each MR changes
  • Backend: Coverlet (built into the xUnit template) produces coverage reports
  • Frontend: Vitest with the Cobertura reporter
  • diff-cover fails the MR if changed lines are below the threshold (for example 80%)
  • GitLab shows covered and uncovered lines directly in the MR diff for reviewers

5Impact Analysis: What Can This Change Break?

  • Frontend: dependency-cruiser / madge show which components use a changed file; vitest related runs only the affected tests
  • Backend: keep shared logic in clear projects and services, and run the full test suite on every MR
  • API contract: generate the Swagger/OpenAPI file during the build and compare it with main using oasdiff. The pipeline fails if a field is removed or renamed or its type changes
  • Optional: generate TypeScript API types from Swagger (openapi-typescript / NSwag), so backend contract changes cause frontend compile errors instead of runtime bugs
Why: The popup and condition bugs most likely came from changing shared code without knowing what else depended on it.

6Pipeline Quality Gates

  • Run backend tests, frontend tests, diff coverage, and Playwright E2E tests in GitLab CI
  • Turn on "Pipelines must succeed" in MR settings so failing MRs can't be merged
  • Optional static analysis: SonarQube Community, strict ESLint + TypeScript, .NET Roslyn analyzers
  • Note: some features (required approvals, Code Owners) depend on the GitLab tier
View example pipeline (.gitlab-ci.yml) 
stages: [.pre, build, test, quality, e2e]

variables:
  GIT_DEPTH: 0

backend-test:
  stage: test
  image: mcr.microsoft.com/dotnet/sdk:8.0
  script:
    - dotnet test ./backend --collect:"XPlat Code Coverage" --results-directory ./coverage
  artifacts:
    paths: [coverage/]
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage/**/coverage.cobertura.xml

frontend-test:
  stage: test
  image: node:20
  script:
    - cd frontend
    - npm ci
    - npx vitest run --coverage
  artifacts:
    paths: [frontend/coverage/]
    reports:
      coverage_report:
        coverage_format: cobertura
        path: frontend/coverage/cobertura-coverage.xml

diff-coverage:
  stage: quality
  image: python:3.12
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - pip install diff-cover
    - git fetch origin $CI_MERGE_REQUEST_TARGET_BRANCH_NAME
    - diff-cover coverage/**/coverage.cobertura.xml frontend/coverage/cobertura-coverage.xml --compare-branch=origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME --fail-under=80

e2e-regression:
  stage: e2e
  image: mcr.microsoft.com/playwright:v1.48.0-jammy  # match your Playwright npm version
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^release/
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - cd e2e
    - npm ci
    - npx playwright test
  artifacts:
    when: always
    paths: [e2e/playwright-report/]

7Feature Flags for Risky Changes

  • Put risky changes to existing features behind a flag, so they can be switched off in production without a new release
  • Backend: Microsoft.FeatureManagement (free, from Microsoft)
  • Frontend + backend: Unleash (open source; GitLab's Feature Flags feature is built on it)

5. Suggested Rollout

Phase 1: Quick Wins

1–2 weeks
  • MR template
  • Ticket-link CI check
  • Branch naming convention
  • Release tags
  • "Bug = new test" rule

Phase 2: Safety Net

3–6 weeks
  • Coverage reports in MRs
  • diff-cover gate
  • Playwright for top 10 critical flows
  • "Pipelines must succeed" enabled

Phase 3: Deeper Checks

2–3 months
  • API contract checks (oasdiff)
  • Integration tests (Testcontainers)
  • Staging environment
  • Feature flags
Ongoing: Tag each regression with the MR that caused it, and review monthly to find weak areas of the codebase.
