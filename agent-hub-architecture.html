01

The constraint that shapes everything

Your three sources are not three flavours of the same thing. Two of them can be called over an API; one of them cannot. Every other decision in this document follows from that.

Agents built in Microsoft 365 Copilot agent builder are declarative agents: instructions, knowledge sources and actions layered on top of the Microsoft 365 Copilot orchestrator. They are surfaced inside Copilot chat and Teams. There is no public endpoint your dashboard can post a user's message to and stream a reply from.

Copilot Studio agents and your org-hosted agents both have real endpoints — Direct Line / the Microsoft 365 Agents SDK client for the former, your own HTTP or MCP surface for the latter. Your dashboard can own the whole conversation for these.

So the hub carries two interaction tiers, and the distinction is visible everywhere — in the Agent Card schema, in the diagram, in the UI, and in what the concierge agent hands back:

TierMeansUser experience in the hubApplies to
Tier A · invocable Gateway holds the conversation: auth, streaming, logging, cost metering, evaluation all happen in your platform. Full chat runner inside the dashboard. Hub can also chain the agent into multi-agent flows. Copilot Studio agents; org-hosted LLM agents; other teams' agents that expose HTTP/MCP.
Tier B · linked Hub holds metadata only. Handoff is a deep link into Copilot or Teams, optionally with the prompt prefilled. Rich catalog entry, worked examples, "Open in Copilot" button. No in-hub transcript, no in-hub telemetry. M365 Copilot agent-builder declarative agents.
Policy implication — decide this in week one

Make it a published rule: if an agent needs to be callable by the platform, by another agent, or by a non-Microsoft surface, it is built in Copilot Studio (or as a custom-engine agent), not in agent builder. Agent builder stays the right tool for lightweight, in-Copilot-only experiences that a business user can maintain themselves.

Without this rule, your catalog slowly fills with agents the platform cannot orchestrate, and the hub degrades into a bookmark list.

One more constraint worth designing around early: the Agents SDK client path for Copilot Studio currently works with delegated (user) authentication — app-only service-principal tokens are not supported. Your gateway therefore cannot be a faceless service calling Copilot Studio on a shared identity; it must perform an on-behalf-of exchange and carry the end user's token downstream. That is better for security and for per-user data boundaries, but it means no unattended/batch invocation of Copilot Studio agents until that changes. Plan scheduled or system-triggered agents on the org-hosted side.

Why the registry and the gateway are separate services

It is tempting to build one service. Don't. They have different consumers, different scaling profiles and different failure modes. The registry is read-heavy, cacheable, and must stay available for the catalog to work; the gateway is long-lived-connection-heavy, holds user tokens, and will be your noisiest component. Keeping them apart also means a gateway outage degrades the hub to a catalog rather than taking it down.

Where the concierge sits

The concierge is deliberately not privileged. It reads the catalog index and the registry through the same APIs as the UI, and it starts sessions through the same gateway. That keeps one enforcement point for entitlements and means anything the concierge can do, a user could have done by hand.

This schema is the product. Routing quality, access control, cost reporting and the onboarding contract all derive from it — get it right before you write any UI.

Most agent catalogues fail because their entries describe what an agent is rather than when to reach for it. The routing block below is what makes the concierge work; treat use_for, do_not_use_for and example_prompts as mandatory fields, reviewed by a human at publish time.

05

The concierge agent

"Tell me which agent to use." A retrieval-and-rank problem with an entitlement filter in front of it — not a general-purpose chatbot, and not a place for open-world generation.

Resolution pipeline

Understand the askNormalise the query, pull the user's department, role and recent agents from context. Detect multi-intent asks and split them.
Filter by entitlementHard filter before retrieval: the candidate set only ever contains agents this user may see. Non-negotiable.
Hybrid retrieveBM25 + vector search over the routing block and example prompts. Top ~20 candidates with scores.
Re-rank with an LLMFull cards for the top candidates go to the model, which weighs do_not_use_for as hard exclusions. Returns top 3.
Answer structurallyRecommendation, confidence, a one-line why, named alternatives, and an explicit handoff action.
Hand offTier A → open a gateway session, optionally carrying the user's original prompt. Tier B → deep link into Copilot or Teams.
LearnLog query, recommendation, whether the user accepted it, and whether the session succeeded. Feeds the eval set and gap mining.

Tools the concierge gets

  • search_agents(query, filters) — entitlement-scoped hybrid search.
  • get_agent(id) — full card, for explaining limits and prerequisites.
  • compare_agents(ids[]) — side-by-side when two candidates genuinely overlap.
  • check_access(id) / request_access(id, justification) — turns a dead end into a ticket.
  • start_session(id, seed_prompt) — Tier A handoff through the gateway.
  • build_deeplink(id, seed_prompt) — Tier B handoff.
  • log_gap(query) — explicit "no agent exists for this" signal.

Guardrails

  • Closed world. The system prompt forbids naming any agent not present in the retrieved set. Agent names are the one thing users will act on, so a hallucinated one is worse than no answer.
  • Refuse-to-guess threshold. Below a confidence floor, the answer is "no good match yet" plus a request-an-agent call to action — and a logged gap. Measure how often this fires; it is your catalog roadmap.
  • Honour the negatives. A do_not_use_for hit excludes a candidate outright rather than lowering its score.
  • Never widen the user's access. Entitlement filtering happens in the search tool, server-side, not in the prompt.

Treat routing quality as a tested property

Build a labelled set of 100–200 real queries → expected agent, harvested from the hub's own search logs and from the service desk. Run it in CI on every change to the router prompt, the index configuration, or the embedding model, and gate releases on top-1 accuracy. Without this, router quality silently decays as the catalog grows — the moment you pass roughly 40 agents, overlapping descriptions start colliding and nobody notices until users stop trusting the recommendations.

Build it twice, or build it once in the right place

Users live in Teams, not in your dashboard. Consider implementing the concierge as a Copilot Studio agent whose tools point at your registry and gateway APIs. You then get the Teams and Copilot surface for free, and the dashboard consumes the same agent through its own gateway — one implementation, two front doors, and the concierge becomes a working reference for every other Tier A integration.

Gateway & invocation contract

One narrow API in front of every agent. Every adapter conforms to it; nothing bypasses it.

EndpointPurposeNotes
POST /v1/sessionsOpen a conversation with an agentReturns session id + capability flags (streaming, file upload, cards). Enforces entitlement here.
POST /v1/sessions/{id}/messagesSend a turnIdempotency key required; files by reference, not inline.
GET /v1/sessions/{id}/streamServer-sent eventsNormalised event types: token, tool_call, card, citation, done, error. Adapters that can't stream emit one token then done.
GET /v1/agents/{id}/handoffTier B deep linkBuilds the Copilot/Teams URL with agent id and optional seeded prompt.
POST /v1/sessions/{id}/feedbackThumbs + free textJoined to the trace; primary quality signal.

Adapter responsibilities

An adapter translates the contract above into one source's reality, and nothing more. Shared concerns — auth exchange, retry, timeout, redaction, content safety, metering, tracing — live in the gateway pipeline so they are implemented once and cannot be forgotten by an adapter author.

  • Copilot Studio adapter. Agents SDK client where streaming matters, Direct Line where it doesn't. Carries the user's delegated token via OBO; maps adaptive cards and citations onto the normalised event types.
  • M365 declarative adapter. No runtime path. Builds deep links, and — where available — pulls agent inventory so the registry can reconcile what exists in the tenant against what's catalogued.
  • Org-hosted adapter. One generic implementation driven by per-agent config: base URL, auth mode, and a request/response field mapping. Because you can't change these agents, the mapping spec is what absorbs their differences — aim to onboard a new one with config only, no code.
  • MCP / A2A adapter. For other teams. Standardise on MCP for tool-shaped agents and an A2A-style card for conversational ones.

Conversation state

Decide explicitly who owns history. Copilot Studio keeps its own conversation state, your org-hosted agents may be stateless, and the hub needs transcripts for audit and evaluation regardless. Recommended: the gateway persists a hub-side transcript for every Tier A session (for audit, feedback and evals) while passing the source's native conversation id through on each turn. Don't try to replay hub history into a source that's already tracking it — you'll double the context and the cost.

07

Onboarding other teams

The hub only stays useful if publishing an agent doesn't require your team. Two paths to the same registry API, one review gate.

Step 1Author

Wizard or agent.yaml

Business owners use a guided form that teaches the routing fields by asking the right questions ("what should someone not use this for?"). Engineering teams commit agent.yaml and publish from CI — same schema, reviewed as a pull request.

OutputA draft card in the registry, visible only to its owners.
Step 2Validate

Automated gates

Schema validation, endpoint reachability, auth handshake, and a smoke run of the declared example prompts. Duplicate detection against the existing catalog by embedding similarity — flag near-identical agents for a conversation rather than letting both ship.

GateAll checks green, or the card cannot move to review.
Step 3Review

Security, data and routing review

Three reviewers, each on a checklist: security (auth, egress, write actions, human-in-loop), data (classification, PII, residency, retention), and catalog stewardship (is the routing block good enough that the concierge will do the right thing?).

GateSign-off recorded on the card version; audit-visible.
Step 4Pilot

Sandbox visibility

Published to a named pilot group only. Concierge may recommend it to that group. Collect real queries and feedback for a fixed window before opening it up.

ExitAgreed pilot volume reached with no blocking feedback.
Step 5Publish

Into the catalog and the index

Card goes live, index is rebuilt, concierge picks it up on the next retrieval. Owners get a dashboard: usage, cost, feedback, eval results, open access requests.

OutputDiscoverable, routable, measured.
Step 6Keep honest

Health, evals, re-review

Scheduled health checks and eval runs. Sustained failures or a missed review_due date auto-flag the card, then auto-unlist it. Owner changes trigger a stewardship handover task rather than silently orphaning the agent.

WhyCatalog rot is the default outcome. This step is what prevents it.

Publish the contract as documentation plus a starter repo: schema, a local validator, an MCP server template, and a conformance test suite teams can run before they ever talk to you. The measure of success for Phase 4 is that a team you've never met gets an agent published without opening a ticket.

08

Identity, security, governance

Identity chain

Entra ID SSO at the hub edge. The gateway exchanges the user's token for a downstream token per agent (on-behalf-of) so that every agent sees the real user and their real permissions. This is the single most important security property of the design: it means a Copilot Studio agent reading SharePoint returns only what that user could already read, and you never have to build a parallel authorisation model over corporate content.

Agent-to-agent calls get their own workload identity, scoped and auditable — not a borrowed user token. If your tenant has Entra Agent ID available, use it rather than inventing service-principal conventions.

Access control, two levels

  • Visibility — whether the agent appears in catalog and concierge results. Default to broad: discoverability is the point of the hub.
  • Entitlement — whether the user may actually run it, backed by a security group. Visible-but-not-entitled is a good state: the user sees the agent exists and gets a "request access" button.

Don't rebuild the Microsoft control plane

Microsoft Agent 365 and the Microsoft 365 admin center now provide tenant-level agent inventory and governance — agent identity, lifecycle, and admin visibility over Copilot Studio and declarative agents. Your hub should consume that inventory, not compete with it.

The split that keeps you out of trouble: Microsoft's control plane answers "what agents exist in this tenant and are they safe?"; your hub answers "what should I use for this task, and how do I run it?" Reconcile against the tenant inventory on a schedule so you can flag agents that exist but aren't catalogued, and catalogued agents that have disappeared.

Data protection

  • Redact detected secrets and configurable PII patterns before prompts reach your own logs — transcripts are the most sensitive thing this platform will hold.
  • Set transcript retention per agent from the card's data block; default short, extend only with justification.
  • Gate publication on data classification: a restricted agent cannot have visibility: org.
  • Require human-in-the-loop declaration for any agent with write-capable tools, and surface that badge in the catalog so users know before they start.
  • Keep Purview/DLP policy in the loop rather than reimplementing it in the gateway.

Observability & cost

Instrument with OpenTelemetry on a three-level span hierarchy — session → turn → tool call — with agent id, source, tier, adapter, user's department and cost attached as attributes. That single trace shape answers almost every question you'll be asked in month three.

QuestionMetricWhy it matters
Is the hub working?Concierge acceptance rate; search-to-session conversionThe core promise is "find me the right agent". This is whether that lands.
Is routing good?Top-1 accuracy on the labelled eval set; "no match" rateGates releases of the router. The "no match" rate doubles as your catalog gap backlog.
Which agents earn their keep?Sessions, unique users, thumbs-up rate, task completion per agentDrives deprecation conversations with owners and exposes duplicates.
What does this cost?Tokens and cost per turn / agent / department; Copilot Studio message consumptionChargeback, and early warning before a popular agent blows a capacity budget.
What's missing?Clustered unmatched queriesThe highest-value product input you will get. Review it monthly with agent owners.
Is anything degrading?p95 latency, error rate, eval regressions per agentFeeds auto-flagging and the owner dashboard.

Note the asymmetry you've accepted: Tier B agents produce almost no telemetry. You will see that a user clicked through to a declarative agent and nothing after that. Report Tier A and Tier B separately rather than averaging them into a number that means nothing — and use the gap as a concrete argument when deciding whether a popular declarative agent should be rebuilt in Copilot Studio.

11

Data model & entitlements

Relational, with the card body in JSONB. But the first decision here isn't SQL versus NoSQL — it's refusing to own data that Entra ID already owns.

Do not store user → agent access in this database

The obvious move is a user_agent_access table. Resist it. Entitlements belong in Entra ID security groups, read from the user's token at invoke time (or from Graph for admin views).

Owning that mapping yourself means owning joiner/mover/leaver provisioning, deprovisioning on a department change, periodic access reviews, attestation reporting — and a long conversation with security about why agent access is the one thing in the org that doesn't flow through the standard path. That is permanent work to avoid a single join.

So the card carries access.entitlement_group, and this database stores the mapping and the paper trail — never per-user rows.

Why relational wins here

It isn't about scale — you have one tenant, a few hundred agents and a few thousand users. It's about the shape of the questions you will be asked, mostly by people who audit things:

Question you'll be askedShape
"Show every agent this user can run, with owner and last review date"3-way join
"Which agents are past review_due and still had >100 sessions last month?"Join + aggregate
"Who approved access to the restricted finance agent, when, and has it expired?"Audit join, strong consistency
"Cost per department this quarter"Aggregate across sessions
"Which card versions did this reviewer sign off?"Join on version history

Every one is a multi-entity join or aggregate with an auditor eventually reading the output. In a document store you would denormalise owners and entitlements into each agent document, then fight drift on precisely the data that gets audited.

Schema

teams              (id, name, contact, steward_upn, escalation)
agents             (id, slug, status, source, tier, owner_team_id, current_version)
agent_versions     (id, agent_id, semver, card JSONB, published_at,
                    superseded_by, created_by, embedding vector(1536))

                   -- kind: security | data | routing

                   -- scope: view | run. Mapping only — no user rows.

                    approver_upn, decided_at, expires_at)
                   -- the audit trail, which genuinely is yours

                    turn_count, total_cost_usd, status, transcript_uri)
turns              (session_id, idx, latency_ms, in_tokens, out_tokens,
                    cost_usd, tool_calls JSONB)

                    accepted, session_id, at)
                   -- doubles as the eval set and the catalog gap backlog
eval_runs          (agent_id, suite, score, at, details JSONB)

JSONB on agent_versions.card is deliberate: the card schema will churn for six months and you do not want forty migrations chasing it. Everything that gets joined or audited stays in columns.

What deliberately isn't in the database

  • Message content. Transcripts go to Blob Storage, referenced by sessions.transcript_uri, with lifecycle rules driven by the card's transcript_retention_days. Prompts are the most sensitive thing this platform holds — keep them out of your OLTP store and out of its backups.
  • Raw telemetry. turns holds metered aggregates for cost attribution only; traces go to Application Insights. Don't let the registry database become a log sink.
  • Per-user entitlement rows. Per the callout above.

Cosmos DB Not recommended Built for global multi-region writes and partition-key-shaped access at scale you will never reach here. You'd trade the audit queries above and predictable cost for nothing you need. Reasonable later as a transcript store if you need to query inside conversations.

.NET 10 implementation notes

  • EF Core 10 + Npgsql. Map the card POCO into the JSONB column with owned-entity JSON mapping, so you get typed access without a migration per schema tweak.
  • Managed Identity to the database. No connection-string secrets in config, Key Vault or pipelines.
  • One JSON Schema for the Agent Card, enforced at both the registry API boundary and the agent.yaml CI check. One contract, two enforcement points — this is what makes §7 self-service work.
  • Entitlement checks are server-side in the gateway only. The React app may hide whatever it likes for UX, but that is cosmetic and must never be the control.
  • React side: MSAL for auth, TanStack Query against the registry API, EventSource for the gateway's SSE stream.
  • Instrument cost from day one even while the budget is central — sessions.total_cost_usd and turns.cost_usd are painful to backfill when chargeback arrives in Phase 5.

Delivery roadmap

Sequenced so the hub is useful at the end of Phase 1 and every phase after that is additive. Durations assume a team of 4–6; phases 2 and 3 can overlap.

Phase 0~3 weeks

Foundations

Inventory every agent that exists today across the three sources and name an owner for each. Design and sign off Agent Card v1. Confirm the Copilot Studio client path and auth model with a throwaway spike. Settle the agent-builder-vs-Studio policy.

Exit criteriaSchema signed off by security and data; every known agent inventoried with a named owner; one Copilot Studio agent invoked from a spike with a real user token.
Phase 1~5 weeks

Catalog MVP

Registry service and API, catalog UI with search and facets, agent detail pages, manual card authoring by the platform team, and Tier B deep-link handoff. No runtime yet — this phase is about making agents findable.

Exit criteria100% of inventoried agents discoverable; a user can find and launch any declarative agent from the hub in under 30 seconds.
Phase 2~6 weeks

Runtime

Agent Gateway with the invocation contract, Entra OBO chain, Copilot Studio adapter with streaming, the config-driven org-hosted adapter, in-hub chat runner, transcripts and audit log.

Exit criteriaThree Tier A agents — at least one per invocable source — running inside the hub with full traces, cost attribution and an audit trail.
Phase 3~4 weeks

Concierge

Catalog index with hybrid retrieval, entitlement pre-filter, LLM re-ranker, structured recommendations with handoff, the labelled routing eval set in CI, feedback capture and gap mining. Ship it to Teams as well as the dashboard.

Exit criteriaTop-1 routing accuracy ≥ 85% on the labelled set; gap report generating automatically.
Phase 4~6 weeks

Self-service

Onboarding wizard, agent.yaml plus CI publishing, automated validation gates, the three-reviewer approval workflow, pilot visibility, owner dashboards, scheduled health checks and auto-flagging.

Exit criteriaA team outside the platform group publishes an agent end-to-end without platform help.
Phase 5ongoing

Scale

MCP and A2A federation, multi-agent chaining where the concierge delegates across agents, cost chargeback, tenant-inventory reconciliation with the Microsoft control plane, ratings and usage leaderboards, and a learned router trained on accumulated acceptance data.

Watch forCatalog growth past ~40 agents is when routing quality and duplicate detection start to really matter.

Decisions to make now

Each of these changes the architecture rather than the implementation, so they're cheap this week and expensive in three months. My recommendation is in the right-hand column.

DecisionOptionsRecommendation
Where does the concierge live? Dashboard only · Copilot Studio agent only · both Build it as a Copilot Studio agent over your registry and gateway APIs, consumed by the dashboard through the gateway. One implementation, available in Teams where users already are.
Agent builder vs Copilot Studio for new agents Free choice · Studio by default · Studio mandatory for anything integrated Studio mandatory when API-callable; agent builder allowed for in-Copilot-only, business-maintained agents. Write it down and enforce it at intake.
Registry vs Microsoft's tenant inventory Build everything · consume Microsoft's · hybrid Hybrid. Your registry owns business metadata and routing; reconcile inventory and identity from the Microsoft control plane. Never duplicate identity governance.
Where do entitlements live? A user_agent_access table in your DB · Entra ID security groups · both Entra ID groups only, referenced by access.entitlement_group on the card — see §11. Expect pushback on "but a table is simpler"; the answer is that a table makes you the owner of joiner/mover/leaver, access reviews and attestation forever.
Does the hub run conversations or just link out? Catalog only · runtime for everything · tiered Tiered, per §1. Resist the temptation to iframe declarative agents into looking like Tier A — you'd inherit the support burden without the telemetry.
Who owns conversation history? Source of record · hub of record · hub transcript + source state Hub transcript for audit and evals, source keeps its own conversation state. Pass the native conversation id through; don't replay history.
Cost model Central budget · chargeback to teams · hybrid Central budget through Phase 3, chargeback from Phase 5. Instrument for chargeback from day one even if you don't bill — retrofitting cost attribution is painful.
Default catalog visibility Private by default · org-visible by default Org-visible by default, entitlement-gated for execution. Discovery is the whole point; a hub where most agents are hidden has no reason to exist.
